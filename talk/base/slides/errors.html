The SDK · Error handling

Where an error happens decides what happens

Inside a step

Retried by the step’s strategy. Each attempt is checkpointed and the invocation ends, so the backoff uses no compute.

Outside a step

The execution is marked FAILED at once. There is no retry.

Retries exhausted

The final error is checkpointed and handed to the handler, which can catch it and carry on.

On replay

The same error comes back at the same point. The step body does not run again.

Step semantics

At least once per retry is the default. At most once per retry never re-runs an interrupted step and reports StepInterruptedError.

The dark panel loops on its own: each pink pulse is a failed attempt, each orange bar is the wait before the next one, drawn to scale so the doubling is visible; after the sixth attempt the error goes to the handler. The practical lesson: wrap anything error-prone in a step, because code outside a step gets no retries. Retries are free in compute terms: the SDK checkpoints the attempt, ends the invocation, and the backend re-invokes when the retry is due. Defaults when you configure nothing: durable.ExponentialBackoff(), six attempts, five seconds doubling to a 60 second cap, full jitter, so each actual delay is a random value up to the figure shown. Other Go presets: durable.NoRetry() and durable.MustLinearBackoff(...). A RetryStrategy is a plain function from RetryAttempt to RetryDecision, so custom ones are easy. Semantics: at-least-once means a step can run twice if Lambda is interrupted after the body ran but before the checkpoint landed, so make steps idempotent. For a payment, use durable.WithSemantics(durable.AtMostOncePerRetry): an interrupted attempt counts as failed, and when no retries remain you get a StepError with ErrorType StepInterruptedError and must check the external system. Invoke takes no retry strategy; wrap it in durable.Retry.
