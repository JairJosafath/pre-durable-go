Errors and the suspension signal

receipt, err := durable.Step(ctx, "charge", charge,
    durable.WithRetry(durable.NoRetry()))

var stepErr *durable.StepError
switch {
case err == nil:
    return receipt, nil
case errors.As(err, &stepErr) &&
    stepErr.ErrorType == "CardDeclinedError":
    return "declined", nil
default:
    return "", err // may be the suspension signal
}

11:15 to 12:15. No clicks. Style: a physics sorter. In the panel, errors drop out of a durable.Step call and fall into one of three bins, bouncing as they land, about nine seconds in all. First a *StepError lands in "typed failure": match it with errors.As. Then a plain error lands in "plain error": an invalid argument or option, such as a Wait under one second, so fix the call. The third token is the suspension signal: it lands, then shoots straight back up and out, because the only correct thing to do with it is return it unchanged. In Go, suspension travels through the error return: when the invocation is about to suspend, the operation hands back a signal error. That is why if err != nil { return zero, err } is not just style here: it is how the invocation ends cleanly at a Wait or a callback. The rule to leave people with: handle the errors you recognize, return everything else untouched. Second point, on the code: a typed failure is rebuilt from the checkpoint, identically on the first run and on replay, so it carries ErrorType and Message rather than your original error value. errors.As against your own CardDeclinedError will not match; compare stepErr.ErrorType. Every operation failure matches *durable.OperationError; sentinels such as ErrCallbackTimedOut, ErrWrongGoroutine and ErrWrongContext match with errors.Is.
