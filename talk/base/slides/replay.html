How it works

Checkpoint and replay

Invocation 1

t = 0 s

step-1

Runs: the body executes and its result is checkpointed

wait-10s

Runs: the timer is checkpointed
and the handler stops here

Invocation ends

The execution stays open,
with nothing running

Suspended for 10 seconds: no invocation, no compute

Invocation 2

t = 10 s

step-1

Replayed: stored result returned, body not run

wait-10s

Replayed: the timer has
already elapsed

Handler returns

Runs: new code, then the execution succeeds

For each operation the SDK looks for a checkpoint and returns it. With none, it runs the operation, serializes the result, persists it, and continues.

2:30 to 3:45. Six clicks; the slide starts with only the title and the bottom line. Click 1: first invocation, step-1 runs for real and its result is persisted through the Lambda checkpoint API. Click 2: the wait is checkpointed. Click 3: the SDK ends the invocation; the execution is still open. Click 4: for ten seconds nothing is running and nothing is billed for compute. Click 5: the service invokes the function again, from the top. This is replay, and both cards arrive together on purpose because replay is near-instant: step-1 does not run its body, it returns the stored result; the wait is already satisfied. Click 6: the code after the wait runs for the first time and the handler returns. Once a checkpoint is persisted that result is safe: if the function is interrupted, replay resumes from the last persisted checkpoint. The same mechanism handles crashes, timeouts, retries and callbacks.
