Goroutines and durable.Go

// wrong: fails with durable.ErrWrongGoroutine
go durable.Step(ctx, "charge", charge)

// right: claim here, run on a child context
fut := durable.Go(ctx, "work",
    func(child durable.Context) (string, error) {
        return durable.Step(child, "step", work)
    })
out, err := fut.Result(ctx)

Map and Parallel fan out the same way: every item or branch gets its own child context, tuned with WithMaxConcurrency and WithCompletion.

durable.Go returns a Future

It claims the child operation on the calling goroutine, then runs the body on a new one.

Await with combinators

All, AllSettled, Any, Race, Join, Select: each records its outcome as one operation.

10:00 to 11:15. No clicks. The dark panel is a looping race and shows what would happen if the SDK allowed plain goroutines on one context. First run: goroutines A and B race to the claim line, A gets there first and takes operation 1, B takes operation 2, and both results are recorded. Replay: this time B wins the race, lands in operation 1 and is handed the result recorded for A's charge; the slots shake and turn pink. That is the bug the SDK refuses to let you write. This is the most Go-specific slide. Determinism says operations must be claimed in the same order every time; goroutine scheduling is not deterministic, so the SDK makes each context single-owner. A plain go statement or an errgroup.Go callback that touches the parent context fails with durable.ErrWrongGoroutine before it claims an operation ID, so nothing is recorded. The check is on in every default build; the durablenocheck build tag compiles it out. durable.Go is the replacement for the go keyword: the claim happens synchronously on the caller, the work happens concurrently on a fresh child context. Inside the body use child, never the outer ctx. Awaiting: do not write a sequence of Result calls that returns on the first error, because the other futures are left unawaited and their progress is not checkpointed when the invocation suspends. Use a combinator; replay then returns the same outcome. For fan-out over data, Map with WithMaxConcurrency is usually what you want; the default completion policy is fail-fast, and CompletionConfig changes that.
