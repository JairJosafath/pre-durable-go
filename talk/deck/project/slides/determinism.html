How it works

Determinism

Goes inside a step

  • The clock: time.Now()
  • Random values and UUIDs
  • API calls and database queries
  • File system access

Only the recorded result takes part in replay.

Code between operations

  • Depends only on the event and on recorded results
  • Never ranges over a Go map to create operations: sort the keys first
  • Passes data through return values, not captured variables
3:45 to 4:30. Style: kinetic type, then a matching diagram. The dark panel plays once, about seven seconds, with both halves running together: on the left three lines land one after another (same operations, same order, every invocation) while on the right three operations appear for the first run and then three for the replay, linked one to one. The left finishes first; about two seconds later two replay operations swap places and the links turn pink: that is a non-deterministic handler. Then two clicks, one per card. This is the one rule everything else follows from. Because the handler re-runs from the top, the sequence of durable operations has to come out identical each time; the SDK validates operation names and types against the checkpoint log during replay. Click 1: anything that can differ between runs belongs in a step body, where only the recorded result matters. Click 2: two Go-flavoured traps. Map iteration order is randomized, so a loop over a map that creates operations will not replay; and a step that mutates a captured variable loses that mutation on replay, because the body does not run again.
