Limits, and what to do about them

256 KB per step result

262,144 bytes per checkpoint. The local test runner enforces the same limit.

1 MB per Invoke input

1,048,576 bytes.

Large payloads

NewFileSystemSerdes writes the value to EFS or S3 Files and checkpoints a reference. Never point it at /tmp.

Custom Serdes

Marshal and Unmarshal, set with WithSerdes or WithStepSerdes, for encryption or compression.

A step result grows until it fills the 256 KB bar (262,144 bytes per checkpoint); past the limit it turns pink and is rejected. Then the fix: with NewFileSystemSerdes the value drops into a file on EFS or S3 Files and only a small reference goes into the checkpoint. There is no state store API: state is the set of operation results in the checkpoint log, so what you return from a step is what you can rely on later. Go's default is durable.JSONSerdes, encoding/json with HTML escaping disabled, so struct tags and unexported fields behave exactly as you expect: an unexported field will not survive replay. The round-trip rule means a value that does not survive JSON shows up on the first run, not as a surprise during replay. The limits come from the service and the local test runner enforces the same ones. Overflow mode only goes to disk above 255 KB; /tmp is wrong because another execution environment may run the replay. A serdes failure is permanent by default; return durable.RetryableSerdesError(err) to mark it transient. Callback results are the exception: raw bytes by default.
